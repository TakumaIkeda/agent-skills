# 単体テスト・統合テスト

テストの価値は「バグを検出できること」と「リファクタリングで壊れないこと」の両立で決まる。
後者を失ったテスト（内部実装を検証するテスト）は、正しいリファクタリングのたびに落ちて信用を失うので書かない。

## 1. 対象コードを分類する

テストを書く前に、対象を次の4つに分類して、方針を決める。

| 分類 | 特徴 | 方針 |
|---|---|---|
| ドメイン・アルゴリズム | ロジックが複雑、外部依存が少ない | **単体テストを厚く書く** |
| オーケストレーション（ユースケース層・ハンドラ） | ロジックは単純、依存が多い | **統合テストを少数書く** |
| 自明なコード | ロジックも依存も少ない（単純なgetter、委譲だけの関数） | **テストしない** |
| 複雑すぎるコード | ロジックが複雑で依存も多い | **テストを書く前に分割を提案する**（ロジックをドメインへ、I/Oを外へ） |

「複雑すぎるコード」に無理にモックを積んでテストを書かない。分割の提案を出して止まる。

## 2. 単体テストの書き方

### 2.1 何を検証するか

- 検証するのは**観察可能な振る舞い**だけ：公開関数の戻り値、返されたイベント、遷移後の状態、返されたエラーのバリアント。
- 内部の関数・private な状態・呼び出し順序は検証しない。
- 「ユニット」はクラスや関数ではなく**振る舞いの単位**。複数の型をまたいでよい。

### 2.2 検証スタイルの優先順位

1. **出力ベース**：入力を渡して戻り値を比較する。純粋関数のワークフローはこれで書く。
2. **状態ベース**：操作した後の状態を、公開されたメソッド経由で確認する。
3. **やり取りベース**（モックで呼び出しを検証）：§4 の条件を満たす場合のみ。

### 2.3 書き方のルール

- Arrange / Act / Assert の3部構成にする。Act は原則1行。Act が複数行必要なら、公開APIの設計が悪いサインとして報告する。
- テスト内に `if` やループを書かない。分岐が必要ならテストを分けるか、パラメータ化する。
- 期待値はハードコードする。プロダクションコードと同じ計算をテスト内で再実装して期待値を作らない。
- テスト名は業務の言葉で、振る舞いを文として書く。
  - ○ `delivery_date_in_the_past_is_rejected`
  - × `test_validate_order_returns_err_when_date_invalid`
- 同じ振る舞いを入力だけ変えて確認する場合は、ケースをテーブル（配列）にまとめる。
- エラーはバリアントで検証する：`assert!(matches!(result, Err(PlaceOrderError::EmptyLines)))`
  エラーメッセージの文字列は検証しない。

### 2.4 網羅の基準

- ワークフローのエラーバリアントは、それぞれ少なくとも1つのテストで発生させる。
- 状態遷移は、許される遷移と、拒否される遷移の代表を両方テストする。
- 値オブジェクトは、不変条件の境界値（ちょうど許される値、ちょうど拒否される値）をテストする。

## 3. 統合テストの書き方

- ユースケース層・ハンドラは統合テストで検証する。
- 本数は、**主要な成功パス1本**（外部とのやり取りを最も多く通るもの）と、**単体テストでは確認できない異常系**（DB制約違反、外部APIの失敗時の振る舞いなど）だけにする。分岐ごとの確認はドメインの単体テストに任せる。
- 自分たちだけが使うDB（管理下の依存）はモックせず、本物を使う。
  `sqlx` を使っている場合は `#[sqlx::test]` でテストごとにDBを分離する。
- Axum のハンドラは `Router` を組み立て、`tower::ServiceExt::oneshot` でリクエストを送って検証する。
- リポジトリ単体のテストは原則書かない（統合テストで通るため）。複雑なクエリがある場合のみ例外とする。

## 4. モック・テストダブル

- モックしてよいのは**管理外のプロセス外依存**だけ：他チームや外部の API、メール送信、メッセージブローカーなど、自分たち以外からも観察される副作用。
- 次はモックしない：
  - ドメインの型、値オブジェクト、同一プロセス内の trait 実装
  - 自分たちのDB（§3 のとおり本物を使う）
- モックは境界の一番外側（外部システムを直接呼ぶ trait）に置く。中間のラッパーをモックしない。
- 外部への呼び出しを検証するときは、**送った内容と回数**を検証し、**それ以外の呼び出しがないこと**も確認する。
- `mockall` より、trait を実装した手書きの Fake / Spy（`Vec` に送信内容を記録する構造体など）を優先する。

## 5. プロダクションコードを汚さない

- テストのためだけに `pub` にしない。private 関数を直接テストしたくなったら、公開 API 経由で検証するか、その関数が独立した概念なら別の型として切り出す。
- テストのためだけのメソッドや `#[cfg(test)]` の分岐をプロダクションコードに入れない。
- 現在時刻・ID・乱数は引数で受け取る設計にする（domain-design スキル §2.3）。グローバルな時計を差し替える仕組みを作らない。
- エンティティに全フィールドの `PartialEq` を derive しない。比較が必要なら ID か個別のフィールドで比較する。ドメインイベントと値オブジェクトは値なので `PartialEq` を derive してよい。

## 6. 配置

- 単体テスト：対象と同じファイルの `#[cfg(test)] mod tests`。
- 統合テスト：クレートの `tests/` ディレクトリ。
- テスト用のデータ生成ヘルパーは `tests/common/` などにまとめる。ヘルパーは「有効なデフォルト値を返し、テストで関心のある値だけ上書きする」形にする。

## 7. 完了前のセルフチェック

テストを書き終えたら、次を確認してから報告する。

- [ ] `cargo test` がすべて通る
- [ ] 各テストについて「振る舞いを変えずに内部実装を書き換えたら落ちるか？」を考え、落ちるものは書き直した
- [ ] ドメインの型・自分たちのDBをモックしていない
- [ ] テスト内に `if` やループ、期待値の再計算がない
- [ ] §2.4 の網羅基準を満たしている

## 8. 報告

次をユーザーに短く報告する。

- 追加したテストの一覧（振る舞いの名前で）
- §1 の分類で「テストしない」「分割を提案」としたもの、その理由
- テストしにくさから見つかった設計上の問題（Act が1行にならない、モックが多すぎる など）
